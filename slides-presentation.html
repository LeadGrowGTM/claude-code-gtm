3.2b
Front-load the use case
WRONG: description: Code review tool RIGHT: description: Review code for bugs, security issues, and maintainability. Speaker Notes
The description field is the single most important thing you write in a skill. Claude scans every skill's description before deciding which to invoke. Three things: what it does, when to use it, and three or more explicit trigger keywords. Front-load the use case in the first 250 characters.
3.3
The moat
## Insider Knowledge - Subject lines under 6 words outperform longer ones for this ICP - Never open with "I" — open with them - Step 2 should reframe, not follow up - Use single-brace variables: {'{'}FIRST_NAME{'}'}, {'{'}COMPANY{'}'}, {'{'}PAIN_POINT{'}'} - No links. No attachments. One CTA max.
Speaker Notes
This section is what makes your skill different from a generic prompt. It encodes what you've learned from running hundreds of campaigns. When you hire a new person, you onboard them. This is how you onboard Claude.
3.3b
Pre-flight checklist
Pattern 1: Description = routing document → WHEN, not just WHAT. 3+ trigger keywords. Pattern 2: Directive, not conversational → Imperative verbs. Numbered steps. Pattern 3: Explicit output format → Define the structure. Same result every time. Pattern 4: Read first → Tell Claude to look before it acts. Pattern 5: Out of Scope section → Name what the skill does NOT do. Pattern 6: Under 500 lines → Long skills lose focus. Split them.
Speaker Notes
These six patterns show up in 100% of skills that work — and are almost entirely absent from skills that don't. Pattern 3 (output format) is where most custom skills fail: they tell Claude what to do but not what the result should look like. Pattern 6 (under 500 lines) is a hard limit — every skill loads into context, and a 2000-line skill costs 5000+ tokens before doing anything.

3.6
Automated QA
## Quality Gates - [ ] Subject line: under 8 words, not a question, not clickbait - [ ] Step 1 body: under 100 words - [ ] Step 2 body: under 80 words, different angle from Step 1 - [ ] No links or attachments in either step - [ ] No "I hope this finds you well" or equivalent - [ ] One CTA max — one question, not a pitch
Speaker Notes
Quality gates are the automated QA layer. Every time this skill runs, these constraints fire. You write them once from your list of things you've had to manually fix. Run the skill 10 times before you consider it done.
3.6b
Fix upstream, not downstream
Mode 1: Wrong direction Claude misread the intent entirely Fix: CLAUDE.md or skill prompt is ambiguous — rewrite it Mode 2: Right direction, bad quality Claude understood but produced mediocre output Fix: Add one real example to the skill One example beats 500 words of instruction Mode 3: Can't tell if it's good No quality standard defined — nothing to check against Fix: Define success criteria in the skill before running "Good = reply rate > 1%, subject < 8 words, no links" Rule: Bad output is a skill authoring problem. Fix upstream.
Speaker Notes
Don't call it debugging — call it output calibration. The fix is almost never in Claude, it's in the skill. Wrong direction: fix the writing. Right direction, bad quality: add one concrete example — Claude pattern-matches faster from examples than from prose. Can't tell if it's good: you never defined what success looks like.

Signals Claude has gone sideways:

  • Actions outside the stated scope
  • Confident assertions it should be reading from a file

GTM Orchestrator — how the campaign actually runs
01 — Source

02 — Signal
Weekly new hire monitor
System checks for new hires at target companies every week. Auto-flags matches.

03 — Relevancy
Role → ICP match + buckets
Which roles signal buyer fit for this client? Companies scored and bucketed by relevance.
→
04 — Value drop
Permissionless intel delivery
"Here are 10 companies hiring [role] that match your ICP." No pitch. Just signal.
→
05 — Close
3-step sequence
Email 1+2: signal intel. Email 3: "Want us to run one free signal-led campaign for you?"
Low volume. High relevance. The free campaign offer sits in email three — by then they've gotten value twice.
Speaker Notes
This is the GTM Orchestrator. Here's how it runs. We start with a signal-led database — curated companies matching the client's ICP. Once a week the system checks for new hires at those companies. Not all hires — we run a relevancy assessment first. What roles, when filled, signal that this company is the right buyer right now? When a company trips that signal it gets bucketed and queued for research. The output is a permissionless value drop — "here are ten companies in your space actively hiring for [role], we think three of them are your best targets this quarter." No pitch. Just signal. The CTA at the end of the sequence isn't "book a call" — it's "we're offering one company a free signal-led campaign this quarter, want us to run yours?" By the time they see that offer in email three, they've already gotten value twice. Lower volume. Higher reply rate. That's the system.
